# Phase 5 — Diverse Double-Compiling (DDC) Defense

## What this proves

`ddc_verify.sh` implements David A. Wheeler's Diverse Double-Compiling
technique and was run against real artifacts from Phases 1/2/4 — not
simulated data. Both the detection case and the no-false-alarm case were
verified for real:

| Run | Result | Exit code |
|---|---|---|
| `./ddc_verify.sh` (against the real infected compiler) | `[ALERT] Discrepancy detected!` — hashes differ, diff shows the exact marker lines | `1` |
| `./ddc_verify.sh --clean-only` (both sides genuinely clean) | `[SUCCESS] Compilers are clean.` — hashes match exactly | `0` |

The second row matters as much as the first: a detector that always says
"ALERT" isn't a detector, it's noise. Confirming a matching hash and a
`0` exit code on a genuinely clean pair proves this script is actually
discriminating between clean and infected, not just alarming by default.

## How the comparison works, concretely

```
compiler_A = g++ clean_source/*.cpp            (trusted compiler, direct build)
compiler_B = g++ (infected_build/tlc --replicate clean_source)   (suspect lineage)

final_A = compiler_A tests/auth.tl -o final_A.cpp
final_B = compiler_B tests/auth.tl -o final_B.cpp

sha256sum final_A.cpp final_B.cpp   -->  compare
```

In the real (alert) run, the actual diff produced was:

```diff
1c1
< // Auto-generated by the TinyLang compiler. Do not edit by hand.
---
> // Auto-generated by the TinyLang compiler (PHASE 2 - marker-injecting build).
5a6,7
>     // [MARKER] this line was injected by the compiler; it does not appear in the TinyLang source
>     std::cerr << "[MARKER_INSERTED by codegen for function: check_login]\n";
```

Note what DDC did **not** need to know in advance: it never had to be told
to look for the word "MARKER," or to know `check_login` was the target
function, or to understand anything about what the injected code does. It
only needed the general property "these two independently-built compiler
lineages should agree when compiling identical input" — and flagged the
disagreement automatically. That's the actual power of Wheeler's technique:
it catches an *unknown* class of divergence, not just a specific signature.

## Adaptation notes (read this before assuming it's "textbook" DDC)

This project's compiler is a source-to-source TinyLang → C++ transpiler,
not something that compiles itself directly to machine code the way a real
C compiler bootstraps itself. Two adaptations were made, both documented
directly in `ddc_verify.sh`'s comments:

1. **"Compiling S with the suspect compiler C"** is implemented as
   `infected_build/tlc --replicate clean_source -o ...` (the suspect
   compiler's own way of processing its kind of source), followed by a
   normal `g++` build of the result into a real binary. `g++` itself is
   treated as a trusted, neutral backend in this threat model — the
   attack surface being tested is entirely "which C++ text does the
   compiler produce," not "how does C++ text become machine code."

2. **"Compile S again through both resulting compilers"** is implemented
   as both compilers compiling the same representative TinyLang test file
   (`tests/auth.tl`) rather than each compiler re-processing its own C++
   source a second time. This was a deliberate simplification: the honest
   `compiler_A` (built straight from `clean_source` with no modifications)
   has no `--replicate` mode at all — real, unmodified compilers don't
   need one — so there is nothing meaningful to compare if the "final"
   step is forced to be self-replication specifically. Using a shared,
   ordinary compilation task as the final step is a fair substitute that
   still captures Wheeler's actual insight: two independently-derived
   compilers, fed identical input, must agree — and if they don't, one of
   the compilers has diverged from expected behavior somewhere in its
   lineage.

## How to run it yourself

```bash
cd infected_build && make all && cd ..   # build the suspect compiler first
./ddc_verify.sh                          # ALERT case
./ddc_verify.sh --clean-only             # SUCCESS / baseline case
```

## The full picture across all five phases

| Phase | What it built | What Phase 5 uses from it |
|---|---|---|
| 1 | Honest TinyLang → C++ compiler | `clean_source/` |
| 2 | Marker-injecting codegen.cpp | embedded inside the infected compiler |
| 3 | C++ quine mechanics | the technique reused to build Phase 4's `main.cpp` |
| 4 | Self-replicating infected compiler | `infected_build/` |
| 5 | This detection harness | proves the infection from Phase 4 is catchable without knowing what it does in advance |
